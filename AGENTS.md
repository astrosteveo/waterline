## GitHub workflow

This project uses GitHub as its system of record. Repository: astrosteveo/waterline (https://github.com/astrosteveo/waterline), default branch main. Project board: "waterline" (https://github.com/users/astrosteveo/projects/15), with the Status columns Todo, In Progress, In Review, Done. Use the `gh` CLI and `git` for everything below.

Read GitHub with REST commands (`gh api repos/astrosteveo/waterline/...`, `gh run list`, `gh run view`) where you can. `gh issue list`, `gh issue view` and `gh pr checks` use GitHub's GraphQL API, whose 5,000 points an hour every agent and tool on the account shares.

Follow these conventions:
- Track work as GitHub issues. Before a change bigger than a typo, find the issue among the open ones (`gh api 'repos/astrosteveo/waterline/issues?state=open&per_page=100'`), and read it with `gh api repos/astrosteveo/waterline/issues/<number>` (its comments with `gh api repos/astrosteveo/waterline/issues/<number>/comments`), or create one with `gh issue create --project "waterline"` and a body with three sections: "### Problem" (what is wrong or missing now, with the evidence), "### Goal" (what the change should do; leave it out when the problem makes that obvious) and "### Acceptance criteria" (a bulleted list of checkable statements that must be true before the issue closes, usually including the tests). These match the issue forms in .github/ISSUE_TEMPLATE/. Label it bug, enhancement or documentation, and priority:high, priority:medium or priority:low.
- Start an issue before working on it. Assign the issue with `gh issue edit <number> --add-assignee @me`. Move it to In Progress on the board with `gh project item-edit --project-id PVT_kwHOAgiNI84Bmw10 --id "$(gh project item-add 15 --owner astrosteveo --url <issue url> --format json --jq .id)" --field-id PVTSSF_lAHOAgiNI84Bmw10zhlYg0c --single-select-option-id 47fc9ee4`. Create its branch `<number>-<slug>`, linked to the issue, with `gh issue develop <number> --name <number>-<slug> --checkout`, or switch to it when it exists. When other agents or sessions may work in this folder at the same time, give the branch a worktree of its own instead, with `git worktree add .claude/worktrees/<number>-<slug> <number>-<slug>`, and work in that folder. Do not work on main directly.
- Reference the issue in every commit message, for example "Add login form (#12)". Make small commits that each leave the project working.
- When the work is ready, push and open a pull request with `gh pr create` whose body includes "Closes #<number>". Write a closing keyword (close, closes, closed, fix, fixes, fixed, resolve, resolves, resolved) right before an issue number only for the issue the pull request finishes; GitHub links any other such mention as a closing reference and closes that issue at the merge. Mention other issues and pull requests as "issue #7" or "see #7" instead, in pull request bodies, issue bodies and commit messages alike. Then move the issue to In Review on the board with `gh project item-edit --project-id PVT_kwHOAgiNI84Bmw10 --id "$(gh project item-add 15 --owner astrosteveo --url <issue url> --format json --jq .id)" --field-id PVTSSF_lAHOAgiNI84Bmw10zhlYg0c --single-select-option-id 280d83da`.
- After every push, check CI with `gh run list --branch <branch>`. Read a failure with `gh run view <id> --log-failed` and fix it before you say the work is done. Don't use `gh pr checks --watch` or `gh run watch`, because they ask GitHub every few seconds until CI finishes; to wait for CI, run `gh run list --branch <branch>` again about once a minute. If the project has no CI workflow, offer to write one under .github/workflows/.
- Keep documentation in the wiki, not in chat. Check it out once with `git clone https://github.com/astrosteveo/waterline.wiki.git .wiki` in the repository root, and keep .wiki/ out of the project's commits. Edit its Markdown files there (Home.md is the front page; a file name is the page title with hyphens for spaces; _Sidebar.md is the navigation), then commit, `git pull --rebase` and `git push` inside .wiki/. Record architecture, decisions and their reasons, setup steps and how-tos there.
- When you notice a bug or follow-up work you will not do now, open an issue for it instead of leaving a TODO comment, and tell the person its number.
- Before you stop working on an issue that is still open, because you hand the work back to the person, move to another issue or run out of context, leave a handoff note in `<common>/github-workflow/notes/<number>-handoff.md`, replacing any earlier one, with three parts headed **Done**, **Left to do** and **Not sure about**. `<common>` is what `git rev-parse --path-format=absolute --git-common-dir` prints, the same folder in every worktree of the repository. Write the file under a temporary name in that folder first, then rename it over the note with `mv -f`. When you start an issue, read its handoff note first.
- When a question blocks your work on an issue and only the person can answer it, such as a product or design decision, write it to `<common>/github-workflow/notes/<number>-question.md`, so the person and every agent on this machine find it. Write the file under a temporary name in that folder first, then rename it over the note with `mv -f`. Tell the person too, then work on something else or stop. Once the person has answered, delete the file.
- Ask the person before you merge a pull request, close an issue, delete a branch or change the board's columns.
